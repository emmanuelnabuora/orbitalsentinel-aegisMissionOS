# ADR-0017: Attribute-Based Access Control

Status: Accepted — 2026-07-28

## Decisions

1. **Two attribute predicates shipped**: clearance dominance over
   classification markings (UNCLASSIFIED < CUI < SECRET), and
   ownership (`is_owner_or_admin`) available for owner-gated mutations.
   Predicates live in `core/abac.py`, orthogonal to RBAC: RBAC answers
   "may this role do this action"; ABAC answers "may this person see
   this object".
2. **Need-to-know applies to everyone — including platform admins.**
   Admins bypass RBAC gates but NOT clearance dominance; an admin who
   creates a SECRET asset cannot read it back without SECRET clearance.
   This is the property government evaluators test first.
3. **Non-leaking enforcement.** Lists filter by
   `classification IN visible_markings(clearance)` at the SQL layer;
   detail reads return 404 (identical body to true absence), never 403.
4. **Expand-then-contract defaults** (ADR-0005): every resource starts
   `unclassified`, every user starts with `unclassified` clearance —
   dominance holds universally until markings are applied, so the
   entire pre-ABAC suite passes untouched (verified: 118 -> 125, zero
   modified tests).
5. **Clearance is admin-set and audited**
   (`PUT /users/{id}/clearance`, action `user.clearance_changed`).
   Marking set at creation; marking *changes* post-creation are a
   follow-up that should route through the Phase 14 approval workflow.

## Consequences

- Adding levels (e.g. TOP SECRET) or compartments (SCI-style caveats)
  extends the ordering/predicates in one module.
- UI renders CUI/SECRET chips; unclassified renders nothing, keeping
  the common case clean.
- Migration `a9c1d3e54f77`; 7 new tests; suite 125 green.
