# Phase 1 — Core Domain + Auth

## Purpose & business value
Everything MissionOS does reduces to statements about missions and the assets
they depend on. This phase makes those first-class, attributable, and
access-controlled — the substrate for MissionIQ scoring, Alerts, and
SentinelAI reasoning.

## User stories & acceptance criteria (verified by tests)
- As an operator I register assets and compose missions from them, with
  per-dependency criticality. ✔ CRUD + attach/detach, 409 on duplicates.
- As a commander I see a mission's dependency graph (mission→asset and
  asset→asset edges). ✔ `GET /missions/{id}/graph`.
- As an admin I manage users and roles; nobody else can. ✔ RBAC tests.
- As a security officer I can attribute every change. ✔ Audit rows with
  actor, request_id, and field-level detail, committed atomically.
- Sessions are safe: rotating refresh tokens, family revocation on reuse,
  generic auth failures. ✔ auth test suite.

## API surface (all under /api/v1, bearer auth)
auth: login, refresh, logout, me · users: create/list (admin)
assets: CRUD + filters (type/status/criticality/search) + dependencies
missions: CRUD + assets attach/detach/list + graph

## Database
Tables: users, user_roles, refresh_tokens, assets, asset_dependencies,
missions, mission_assets, audit_log. String-backed enums (portable, ALTER-free
member additions), UUID keys, timestamped, FK cascades chosen per relation.
Migration `d4821a972524` is autogenerated from models and verified by
applying to a fresh database, then seeding through the real service layer.
